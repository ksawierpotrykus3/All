## FAKTY KLUCZOWE

### 1. BaseLinker API — limit 100 req/min, ~150 metod, kluczowe dla integracji

- **Fakt:** BaseLinker API ma twardy limit **100 zapytań na minutę**. API komunikuje się przez POST na `https://api.baselinker.com/connector.php`, autoryzacja przez nagłówek `X-BLToken`. API pokrywa ok. **150 metod** obejmujących zamówienia, produkty, magazyn, przesyłki, faktury, zwroty, CRM.
- **Źródło:** https://api.baselinker.com/ — *"Request limit The API request limit is 100 requests per minute. Latest changes The API was last updated 2026-03-16."* Oraz lobehub.com: *"BaseLinker rate limit is 100 requests/min; the client throttles to stay under it. Method coverage All ~150 documented methods across Orders, Invoices, Receipts, Order Returns, Courier Shipments, CRM, Product Catalog (Inventory)..."*

- **Fakt:** Współdzielenie tokena API między wieloma aplikacjami może powodować przekroczenie limitu 100 req/min i błędy synchronizacji. Konwerter KTsoft explicite ostrzega: *"Jeżeli jednak inna aplikacja korzysta z tego samego tokenu w tym samym czasie to limit może zostać przekroczony i pojawi się komunikat o treści zbliżonej do..."*
- **Źródło:** doc.ktsoft.pl (Moduły wejściowe import z handlowego) — https://doc.ktsoft.pl

- **Fakt:** BaseLinker oferuje moduł „Akceleracje" pozwalający na zmianę limitu API (podniesienie ponad standardowe 100 req/min) w ramach wyższych planów.
- **Źródło:** https://base.com/blog/akceleracje-baselinker — *"Zmiana limitu zapytań API BaseLinker - 100 zapytań na minutę (standard) ... W ramach modułu możesz łatwo sprawdzić historię zmian częstotliwości synchronizacji oraz limitów zapytań API"*

---

### 2. Apilo API — REST, OAuth 2.0, token ważny 21 dni, brak publicznego limitu

- **Fakt:** Apilo udostępnia oficjalne REST API. Autoryzacja odbywa się przez **OAuth 2.0** (Authorization Code / Refresh Token). **Access token jest ważny 21 dni** — po tym czasie wymagane jest odświeżenie przez `POST /rest/auth/token/` z `grantType: "refresh_token"`. Aplikację tworzy się w panelu: Administracja → Klucze API Apilo → Nowa aplikacja REST API.
- **Źródło:** https://packagist.org/packages/apilo/apilo-api-php — *"Access token is valid for 21 days therefore in order to maintain an active connection to the REST API it is necessary to send a request consisting of token pair..."* Oraz https://developer.apilo.com/api/

- **Fakt:** Apilo API nie publikuje sztywnego limitu req/min w oficjalnej dokumentacji. Ograniczenia wynikają z filtrów paginacyjnych (np. `orderedAfter`, filtr `limit` przy pobieraniu listy zamówień).
- **Źródło:** https://apilo.com/pl/pomoc (API Zamówienia) — *"Filtr orderedAfter pozwala na ograniczenie wyników do zamówień złożonych po określonej dacie, co może znacznie poprawić wydajność i szybkość odpowiedzi API. ... Zaleca się korzystanie z filtra limit przy pobieraniu listy zamówień."*
- **Status:** Nie potwierdzono oficjalnego limitu req/min dla Apilo API — brak w publicznej dokumentacji.

### 3. Shopify API — REST jest legacy, GraphQL to standard, REST kończy się w 2026

- **Fakt:** **Shopify REST Admin API jest legacy od października 2024** i otrzymuje wyłącznie poprawki bezpieczeństwa. Od 1 kwietnia 2025 wszystkie nowe publiczne aplikacje muszą być budowane wyłącznie w oparciu o **GraphQL Admin API**.
- **Źródło:** https://shopify.dev (Checkout — *"The REST Admin API is a legacy API as of October 1, 2024. Starting April 1, 2025, all new public apps must be built exclusively with the GraphQL Admin API."*)

- **Fakt:** Shopify wersjonuje API **kwartalnie**. Aktualne stabilne wersje to m.in. `2026-01`, `2026-04`, `2026-07`. Każda wersja ma określony czas życia — np. `2026-01` dostępna do 16 stycznia 2027, `2026-04` do 1 kwietnia 2027. Aplikacje używające przestarzałych wersji są automatycznie routowane do najbliższej stabilnej wersji.
- **Źródło:** https://shopify.dev/docs/api/usage/versioning — *"Stable version | Release date | Accessible until ... 2026-01 | January 1, 2026 | January 16, 2027 15:00 UTC 2026-04 | April 1, 2026 | April 16, 2027 15..."* Oraz Workato docs: *"any API calls requesting for 2025-04 version are automatically routed to the 2025-07 version by Shopify."*

- **Fakt:** **Limity Shopify GraphQL:** standardowy sklep ma bucket 1 000 punktów, restore rate 50 pkt/s; Shopify Plus: 2 000 punktów, 100 pkt/s. REST: 40 req/s na aplikację. Przekroczenie = HTTP 429.
- **Źródło:** https://improvado.io/blog/shopify-api — *"Rate limits (40 requests per second for REST, 1,000 points per second for GraphQL)"* Oraz https://shopify.dev (throttleStatus: *"Standard shops = 100 points bucket, 50/s restore; Plus = 1000/100"*)

- **Fakt:** Od 1 stycznia 2026 **nowe „legacy custom apps" tworzone w panelu Shopify admin zostały wycofane**. Nowe aplikacje należy tworzyć przez Dev Dashboard.
- **Źródło:** https://hermes-agent.nousresearch.com (Shopify skill) — *"As of January 1, 2026, new 'legacy custom apps' created in the Shopify admin are gone. New setups should use the Dev Dashboard."*

## RYZYKA I PUŁAPKI

### Ryzyko 1: Limit 100 req/min w BaseLinker API — wąskie gardło przy dużej skali
Przy intensywnej synchronizacji (setki zamówień dziennie, wiele kanałów jednocześnie) limit 100 req/min może być niewystarczający. Problem potęguje się, gdy ten sam token API jest używany przez wiele aplikacji jednocześnie. **Ryzyko:** błędy 429, opóźnienia w synchronizacji, konieczność wykupienia modułu „Akceleracje". Źródło: https://api.baselinker.com/ oraz https://doc.ktsoft.pl

### Ryzyko 2: Shopify REST API jest w fazie wygaszania — migracja do GraphQL jest konieczna
Jeśli klient ma integracje oparte na Shopify REST API (a wiele starszych wtyczek i customowych rozwiązań tak ma), **będą one wymagały migracji do GraphQL**. REST Admin API jest legacy od 2024 i otrzymuje tylko security fixes. Nowe aplikacje muszą być budowane w GraphQL. **Ryzyko:** starsze integracje przestaną działać, konieczna przebudowa. Źródło: https://shopify.dev

### Ryzyko 3: Shopify — kwartalne wersjonowanie API wymusza ciągłe utrzymanie
Shopify co 3 miesiące wydaje nową wersję API i wygasza starsze. Każda integracja wymaga regularnych aktualizacji (np. `2026-01` wygasa 16 stycznia 2027). **Ryzyko:** bez ciągłego monitoringu changelogów integracja „cichnie umiera" — zaczyna zwracać błędy deprecjacji lub nieprawidłowe dane. Źródło: https://shopify.dev/docs/api/usage/versioning

### Ryzyko 4: Nowe zmiany regulaminowe Allegro REST API (1 września 2026) — 1 klucz API
Od 1 września 2026 można mieć tylko **1 klucz REST API** (zamiast 5). To poważne ograniczenie dla firm, które mają wiele integracji (np. ERP + WMS + własne skrypty). Każda dodatkowa integracja wymaga indywidualnego wniosku. **Ryzyko:** brak możliwości uruchomienia wielu niezależnych integracji bez dodatkowych starań. Źródło: https://developer.allegro.pl/news/1-wrzesnia-zaktualizujemy-regulamin-allegro-rest-api-E7ngjnmGXhY

### Ryzyko 5: Wymóg nagłówka User-Agent w Allegro API (od lipca 2026)
Każde żądanie do Allegro REST API musi zawierać nagłówek `User-Agent` z nazwą aplikacji, wersją i adresem URL. Starsze integracje, które tego nie robią, **będą odrzucane**. **Ryzyko:** konieczność modyfikacji wszystkich klientów API. Źródło: https://ppmag.pl oraz https://www.selly.pl

### Ryzyko 6: Token Apilo API ważny tylko 21 dni — wymaga automatycznego odświeżania
Access token Apilo wygasa po 21 dniach. Bez zaimplementowanego mechanizmu refresh tokena integracja przestanie działać. **Ryzyko:** przestój w synchronizacji, konieczność ręcznej interwencji. Źródło: https://packagist.org/packages/apilo/apilo-api-php

### Ryzyko 7: Brak oficjalnego limitu Apilo API — nieprzewidywalność
Apilo nie publikuje sztywnego limitu req/min. Przy intensywnym odpytywaniu API może dojść do throttlingu po stronie Apilo. **Ryzyko:** trudność w zaprojektowaniu wydajnej synchronizacji bez wiedzy o limitach. **Status:** Nie potwierdzono oficjalnego limitu — brak w publicznej dokumentacji.

### Ryzyko 8: Make.com — koszty kredytów rosną szybko przy złożonych scenariuszach
10 000 kredytów w planie Core może zostać wyczerpane szybko przy wielokrokowych scenariuszach z pętlami (np. aktualizacja 200 produktów = 200+ operacji). **Ryzyko:** konieczność przejścia na wyższy plan (Pro/Teams) = wyższy koszt miesięczny. Źródło: https://www.lindy.ai/blog/make-com-pricing oraz https://apps.make.com/shopify

## AMUNICJA DO OFERTY

### 1. „Wiem, że Shopify REST umiera — proponuję GraphQL"
Warto pokazać klientowi, że rozumiemy kierunek rozwoju Shopify: REST Admin API jest legacy od 2024, nowe aplikacje muszą być budowane w GraphQL. Jeśli klient ma stare integracje REST, zaproponujmy migrację **zanim** Shopify całkowicie wyłączy REST. To buduje wizerunek eksperta, który wyprzedza problemy.

### 2. „Uwaga na nowe zasady Allegro API — 1 klucz od września 2026"
Od 1 września 2026 Allegro drastycznie ograniczyło liczbę kluczy REST API (z 5 do 1). Jeśli klient ma wiele integracji opartych na osobnych kluczach, **będzie potrzebował wsparcia w konsolidacji lub wnioskowaniu o dodatkowe klucze**. Możemy zaproponować audyt kluczy API jako element usługi.

### 3. „BaseLinker ma limit 100 req/min — przy Twojej skali to może być za mało"
Jeśli klient operuje na dużych wolumenach, warto uświadomić mu, że standardowy limit BaseLinker API to 100 req/min. Przy wielu kanałach i intensywnej synchronizacji **konieczne może być wykupienie modułu Akceleracje** lub optymalizacja liczby wywołań. To pokazuje, że myślimy o skali, a nie tylko o „podłączeniu".

### 4. „Apilo token wygasa po 21 dniach — potrzebny auto-refresh"
Warto wspomnieć, że Apilo API wymaga implementacji mechanizmu odświeżania tokena co 21 dni. **Bez tego integracja przestanie działać po 3 tygodniach.** To konkret, który pokazuje praktyczną wiedzę.

### 5. „Make.com to nie tylko klikanie — to koszty kredytów"
Klient może nie zdawać sobie sprawy, że Make.com rozlicza się za operacje (kredyty). Przy złożonych scenariuszach (np. aktualizacja setek produktów) plan Core (10 000 kredytów) może być niewystarczający. Warto zaproponować **optymalizację scenariuszy pod kątem zużycia kredytów** jako element wartości dodanej.

### 6. „BaseLinker vs Apilo — dobór zależy od wolumenu i integracji"
BaseLinker ma ponad 1 700 integracji, Apilo — ponad 600. BaseLinker wygrywa przy sprzedaży na 3+ marketplace'ach, Apilo — przy średnich wolumenach z naciskiem na logistykę i prostotę. Możemy zaproponować **rekomendację systemu na podstawie analizy wolumenu i kanałów klienta**.

- **WebAPI oferuje dwa typy kontrolerów**:
  - **Dynamiczne** – automatycznie generowane z modelu danych enova365; mapują standardowe obiekty (produkty, kontrahenci, dokumenty, magazyny) na endpointy REST bez pisania kodu.

## Odpowiedź na pytanie techniczne klienta (do oferty)

**Jak podejść do udostępnienia marży, skoro enova wylicza ją obiektowo?**

Marża w enova365 jest wynikiem działania workerów przeliczających (tabele `ObrotyPozycji`, `ObrotyTransakcji`), a nie polem przechowywanym w bazie. Są dwa podejścia:

1. **Kontroler dynamiczny + odczyt tabel obrotów** — jeśli workery są uruchomione i tabele są aktualne, można wystawić dane przez kontroler dynamiczny mapujący tabele obrotów. Ryzyko: zależność od harmonogramu workerów.

2. **Własny kontroler statyczny (.NET SDK enova365)** — wywołanie logiki obiektowej enovy bezpośrednio przez SDK, pobranie marży wyliczonej przez system i wystawienie jej przez WebAPI. To podejście rekomendowane — daje spójność z logiką systemu i nie zależy od stanu tabel stagingowych.

**Rekomendacja:** podejście 2 (kontroler statyczny) jako docelowe, z opcją 1 jako fallback.

===== OFERTA =====
Dzień dobry,

Marża w enova365 to nie pole w bazie, tylko wynik działania workerów przeliczających tabele obrotów. Klient, który wystawia dane przez zwykłe mapowanie kolumn SQL, dostaje wartości, które potrafią się rozjechać z tym, co system pokazuje na formularzu. To jest realny problem w tym projekcie i on wymaga obejścia przez SDK, a nie kolejnego SELECT-a.

Punkt pierwszy, czyli pytanie o marżę, rozwiązujemy tak: własny kontroler statyczny w .NET, osadzony na serwerze WebAPI, który wywołuje logikę obiektową enovy i wystawia marżę już policzoną przez system. Kontrolery dynamiczne zostawiamy do tego, co faktycznie potrafią wystawić z modelu danych, czyli dokumenty sprzedaży, zapytania ofertowe i rozrachunki. Dynamiczne generują się z definicji dokumentów na Waszej instalacji, więc zewnętrzna warstwa dopasowuje się do Waszych struktur, a nie odwrotnie. Swagger z Waszego serwera jest tu źródłem prawdy co do dostępnych endpointów, bo to konkretny build 2512.2.2, a zachowanie kontrolerów dynamicznych zmieniało się między wydaniami.

Dalej cykliczne eksporty. Zamiast odpytywać ERP w kółko, spokojnie można oprzeć to o Harmonogram Zadań, który sam się odzywa przy zmianie statusu czy danych. Trzy strumienie: sprzedaż z marżą w podziale na klienta, rynek i handlowca, zapytania ofertowe ze statusem, rozrachunki z przeterminowaniami. Każdy zapis do zewnętrznych tabel z walidacją, żeby warstwa analityczna nie dostała śmieci. Autoryzacja idzie przez JWT z użytkownikiem integracyjnym, nie przez login człowieka, z proaktywnym odświeżaniem tokenu.

Warto sprawdzić jedną rzecz po Waszej stronie: czy reseller faktycznie aktywował moduł WebAPI na instalacji. Wersja platynowa zwykle go zawiera, ale to nie jest tak, że włącza się sam. Jak będzie potwierdzenie aktywacji, ruszamy od razu.
